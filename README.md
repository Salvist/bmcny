## Admin workspace

Open `https://admin.bmcny.church/` or `http://admin.localhost:3000/` locally.
Home summarizes event announcement visibility and recent prayer requests. Shared
navigation links to `/events` and `/prayer-requests`; create events at
`/events/new` and edit them at `/events/:id`. Saving or cancelling returns to
Events. Sign-in remains separate at `/login` and uses the existing admin allowlist.

Event visibility uses New York calendar dates, including both display boundaries.
The prayer summary counts the preceding 168 hours, including across daylight
saving changes. Preview links locate the request's current inbox page; requests
can be managed in the inbox, where contact information is also available.

The workspace uses the events and prayer request tables. Apply the prayer
request field migration described below; no additional environment variable is needed.

## Prayer requests

The public form is available at `/prayer-request` (English) and
`/id/prayer-request` (Indonesian). Name is optional; an email address or phone
number and a prayer request are required. The private admin inbox is at
`https://admin.bmcny.church/prayer-requests`, using the existing admin allowlist.
For local admin access, use `http://admin.localhost:3000/prayer-requests`.

### Database rollout

Before deploying the new pages, apply
`supabase/migrations/20261107174233_create_prayer_requests.sql` to the same Supabase
project used by the app. The existing `public.admin_users` table and its admin
read policy must already be installed. The migration creates the prayer request
table, validation constraints, ordering index, and access policies.
Also apply `supabase/migrations/20261107195000_update_prayer_request_fields.sql`
before deploying this update. It preserves existing submissions, separates phone
and email, and adds automatic updated dates, status, and private notes.
Admins can save status (Pending, Ongoing, Prayed, Rejected) and notes in the inbox.

If your Supabase project is already linked and its migration history matches
this checkout, use the Supabase CLI migration workflow. Otherwise, run the
required migrations in order in the target project's Supabase SQL Editor; do not blindly
push the older local migrations into an existing database.

Reuse `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.
No service-role key or additional environment variable is required. Visitors
can insert requests but cannot read, update, or delete them. Only authenticated
users on the admin allowlist can read requests and update status and notes. Request IDs and timestamps are
generated by the database and cannot be supplied by visitors.

### Verification

Run `npm test`, `npx tsc --noEmit`, and `npm run build`. In a test Supabase project,
submit a request with an email and another with a formatted phone number;
confirm that success clears the form, errors preserve entries, and both appear
in the admin inbox. Check both languages, mobile navigation, the inbox's empty
state, and pagination with more than 50 requests. Verify that anonymous users
and authenticated users outside the admin allowlist cannot read submissions,
and that no public update or delete is permitted.
